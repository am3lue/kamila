# 02.2 — Tool Permission Redesign

## Objective

Replace the binary "ask for every shell command, allow everything else" model with a declarative, persistent permission policy. Every tool call is checked against a policy: **allow** (no prompt), **deny** (blocked), or **ask** (confirm once, remember decision for the session/tool+arg pattern). This is the security foundation `05.3-permission-model` will formalize further.

## Current State

- `run_shell_command` is the *only* tool with any gate: a `readline(stdin)` y/N prompt (`src/ai/tools.jl:44-51`), now fixed by `02.1`.
- All other tools (`write_file`, `delete` via shell, `web_search`, `set_reminder`, ...) execute with no policy at all. There is no `safe_delete_file`-style tool; deletion is only reachable via `run_shell_command`.
- `force=true` is a free parameter any caller (including a compromised model prompt) can set (`src/ai/tools.jl:42,53`).
- No allowlist persists; every session re-asks. No audit log of what was allowed/denied.

## Design

- **Policy file** `~/.kamila_policy.json`:
  ```json
  {
    "version": 1,
    "rules": [
      {"tool": "run_shell_command", "match": "ls|cat|pwd", "action": "allow", "scope": "pattern"},
      {"tool": "run_shell_command", "match": "rm|mv|shutdown|reboot|mkfs|sudo", "action": "deny", "scope": "pattern"},
      {"tool": "write_file", "match": "*", "action": "ask", "scope": "tool"}
    ],
    "default_action": "ask",
    "session_remember": true,
    "max_asks_per_session": 20
  }
  ```
- **Decision engine** `Permission` (`src/security/permission.jl`): given `(tool, args)`, first match wins in rule order; then `default_action`. Returns `:allow | :deny | :ask`.
- **Session cache**: within a process, decisions for identical `(tool, normalized_args)` are remembered when `session_remember=true`, so an agent doesn't re-prompt for the same action 10 times (this is what makes multi-step tasks usable).
- **Capability tokens**: `force` is no longer a free flag. A tool call may carry `capability` = a signed token (`HMAC` with a per-session secret) only produced by the `Permission` engine when the policy yields `:allow`. `force` without a token ⇒ treated as `:ask`/`:deny` per policy.
- **Audit:** every decision is emitted as a structured log event (see `01.3`) — `{"event":"permission.decision","tool":...,"action":...,"policy_rule":...}`.
- **Defaults on first run:** write the starter policy above; expose `Permission.get_policy()`/`Permission.set_policy()` and a bridge route `permission.get/set` so the TUI can edit rules.

## Risks & Mitigations

- **Risk:** Users lock themselves out (deny everything). **Mitigation:** `default_action=ask` (not deny) for unknown, and a documented recovery path (`Permission.reset_policy()` via `bin/kamila --reset-policy`).
- **Risk:** Pattern rules too clever (regex on command strings). **Mitigation:** start with word-boundary prefix matching (a command-name rule like `rm` never matches a substring inside another word, e.g. "confirm"); extend carefully in `05.3`.
- **Risk:** Session cache forgets mid-task. **Mitigation:** cache only exact `(tool, normalized args)` pairs, capped at 100 entries.

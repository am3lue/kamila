# 02.5 — Parser Hardening

## Objective

Make the text-JSON tool-call parser robust enough to trust in production, since it remains the primary agent→tool bridge until `05.1-native-function-calling` replaces it. Hardening = never crash on malformed output, never mis-parse a legitimately nested structure, and always prefer real tool results over hallucinated ones.

## Current State

- `Agent.parse_response` (`src/ai/agent.jl:138-212`): regexes for fenced JSON, then a greedy `match(r"(\{.*\})"s, ...)` fallback, then a **global regex cleanup** `replace(json_str, r",\s*([}\]])" => s"\1")` (`src/ai/agent.jl:164`) that can corrupt strings containing `",` inside them (e.g. `"greeting": "hi, then", "next": 1` becomes `"hi then"`).
- Trailing-comma handling is ad-hoc; nested `}` in strings breaks the greedy `{.*}` match.
- `AgentStream.parse_response` (`src/ai/agent_stream.jl:210-234`) is a second, subtly different copy (extracts `thought` from the JSON rather than the surrounding text).
- Fuzzy alias mapping (`normalize_tool_name`, `src/ai/tools.jl:859-883`) masks typos but can silently map to the wrong tool.
- Duplicated logic = two drift-prone parsers.

## Design

- **Single canonical parser** `src/ai/response_parser.jl` used by both `Agent` and `AgentStream`:
  - Extract candidate JSON blocks: fenced blocks first; then balanced-brace scanning (a small state machine that respects strings and escapes) instead of greedy `{.*}`.
  - **Post-process via a real JSON repair only where safe**: remove trailing commas using a brace/string-aware tokenizer (skip commas directly before `}`/`]` *outside* of strings), never a global regex.
  - If `JSON.parse` fails on a candidate, try the repair; if it still fails, record `parse_error` (structured log) and move to the next candidate.
  - Extract `thought` from the **surrounding text** (fences removed), falling back to a `thought` key inside the JSON only if the text is empty — consistent behavior across both agents.
- **Deterministic tool-name resolution:** map alias → canonical once at registry build (`get_all_tools`), and have `execute_tool` require an exact canonical match (typo suggestions returned, not silent aliasing).
- **Contract validation:** after parsing, verify required args per tool schema (from the `Tool` description) before calling; missing required arg → categorized `:validation` error returned to the agent so it can self-correct.

## Acceptance Criteria

- [x] Parser never throws on any input string (fuzz test: 1,000 random strings, incl. JSON-ish garbage).
- [x] A string value containing `", }` and ``,]` round-trips unchanged.
- [x] Both agents use the same parser (single include, no duplicated logic).
- [x] Missing required args produce a `:validation` error message back to the agent, which can self-correct in the next loop iteration.
- [x] Alias typos produce a suggestion, never a silent wrong-tool call.

## Risks & Mitigations

- **Risk:** Balancing braces is subtle; performance on long outputs. **Mitigation:** linear single-pass scanner; cap scanning at 50 KB of accumulated response.
- **Risk:** Behavior change breaks existing conversations (models "rely" on loose parsing). **Mitigation:** the canonical parser accepts strictly *more* inputs (string-safe repair); keep `normalize_tool_name` behavior for canonical aliases users depend on.
- **Risk:** Fuzz test flakes. **Mitigation:** deterministic seed; failures assert the parser *returns* rather than specific values.

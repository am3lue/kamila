# 02.1 — Stdin/Bridge Conflict Fix

## Objective

Eliminate the architectural conflict where `run_shell_command` blocks on `readline(stdin)` while the bridge process is simultaneously consuming stdin for the JSON-RPC protocol. The result: shell commands can be confirmed safely whether Kamila runs in bridge mode (TUI) or interactive mode, with zero protocol corruption.

## Current State

- `run_shell_command` prompts interactively: `print("Allow? (y/N/! = force): ")` then `user_response = strip(readline(stdin))` — `src/ai/tools.jl:44-51`.
- The bridge reads the **same** stdin for JSON-RPC requests: `readline_timeout(stdin, read_timeout)` in the main loop — `src/bridge.jl:852-868`, dispatched at `src/bridge.jl:870-893`.
- Consequence: inside bridge mode the tool's `readline` steals a protocol line (or blocks forever); outside bridge mode there is no per-command policy and no audit trail.
- Additionally, the confirmation `println` banner goes to **stdout** (`src/ai/tools.jl:44-47`), which is the protocol channel — this corrupts the JSON stream whenever the agent calls `run_shell_command` under the TUI.

## Design

- Introduce a **confirmation service** `Confirm` (`src/system/confirm.jl`) with pluggable backend:
  - `InteractiveConfirm` — the current CLI prompt, but writing the prompt to **stderr** and reading a line.
  - `BridgeConfirm` — emits a JSON `{"type":"confirm_request","id":...,"tool":"run_shell_command","command":...}` on stdout and waits for a `{"type":"confirm_response","id":...,"allow":bool}` **on stdin** via a side-channel that the bridge main loop knows not to treat as a protocol request.
- The bridge main loop gains a `pending_confirm` registry keyed by request id; when a protocol line is a `confirm_response`, it resolves the pending confirmation instead of dispatching it.
- Pre-approval allowlist (`~/.kamila_allowlist.json`) checked before prompting; matches skip confirmation entirely. See `02.2-tool-permission-redesign` for the policy model.
- `force=true` parameter semantics preserved: only honored if the caller carries a capability token issued by `02.2`.

## Risks & Mitigations

- **Risk:** Race between `confirm_response` arriving and the tool's await loop. **Mitigation:** single-threaded bridge loop; confirmations resolved synchronously in the main loop, not in the tool thread.
- **Risk:** Allowing an existing TUI (older version) that never sends `confirm_response` to wedge. **Mitigation:** timeout-to-deny default means older TUIs simply get denials, not hangs.

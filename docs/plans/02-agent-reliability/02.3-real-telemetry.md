# 02.3 — Real Telemetry

## Objective

Remove all fabricated/fake metrics so Kamila never reports data it did not actually measure. This is a trust requirement: an assistant that reports `rand(10:80)` as CPU usage is not just wrong — it is dishonest, and that dishonesty is disqualifying for any later autonomy/learning work.

## Current State

- `get_cpu_usage` falls back to `return round(rand(10:80), digits=1)` when `/proc/stat` parsing fails — `src/system/monitor.jl:139-171`. It also computes a *snapshot* usage from a single `/proc/stat` read, which is meaningless (delta-based usage needs two samples).
- `get_running_processes` shells out to `ps aux --no-headers | wc -l` (`src/system/monitor.jl:297-304`) — acceptable but unlabelled.
- `get_disk_usage`/`get_directory_usage` walk the whole home dir (`src/system/monitor.jl:177-231`) — expensive and can be reported as wrong if interrupted.
- `monitor_resources` prints to stdout with `print("\r...")` (`src/system/monitor.jl:429-435`) — protocol risk when running under the bridge.
- `get_internet_latency` returns `-1.0` on failure (`src/system/monitor.jl:555-564`) — an overloaded sentinel that callers may misread as a real latency.

## Design

- **Delta-based CPU**: `get_cpu_usage()` keeps a module-level last-sample of `/proc/stat` (jiffies + timestamp); usage = (current - last)/(elapsed). First call returns `nothing` after recording the baseline.
- **Explicit unknowns**: every metric returns `nothing` (or `"unknown"`) when it cannot be measured. JSON serialization renders `nothing` as `null`. Never random.
- **Cache directory stats**: `get_directory_usage` honors a cache TTL (default 5 min) keyed by path, invalidated on mtime change of the top dir.
- **Latency sentinel**: replace `-1.0` with a `Result`/`nothing`-based API (`get_internet_latency()::Union{Float64,Nothing}`).
- **No stdout writes** from monitor code; `monitor_resources` writes to stderr via `KamilaLog` (`01.3`) instead of `print`.
- **Label every metric source** in `system_status` output: `(measured)` vs `(unavailable)`, so the TUI/user can see confidence.

## Risks & Mitigations

- **Risk:** Delta CPU means the first `system_status` shows `unavailable`, confusing users. **Mitigation:** `system_status` prefetches a baseline on startup so the first user-facing call is already a real delta.
- **Risk:** Cache invalidation staleness. **Mitigation:** TTL short (5 min) + mtime-based invalidation; documented in the tool description.

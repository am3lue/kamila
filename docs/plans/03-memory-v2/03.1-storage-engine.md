# 03.1 — Storage Engine

## Objective

Introduce a durable, queryable, transactional storage engine for memory (replacing the single `~/.kamila_memory.json` blob) while keeping JSON export/import for compatibility. This is the substrate every other memory plan (embeddings, episodic, injection) and downstream category (planning, autonomy, learning) builds on.

## Current State

- All state lives in one JSON file `~/.kamila_memory.json` (`src/Kamila.jl:19`), read/written wholesale by `KamilaMemory.load_memory/save_memory` (`src/memory/memory.jl:46-72`).
- `TaskManager` serializes tasks through the same blob (`src/tasks/task_manager.jl:33-84`); every `save_memory` rewrites the whole file (write amplification, corruption risk on crash).
- No concurrency safety, no migrations, no indexes. `get_memory_stats` recomputes everything by scanning arrays (`src/memory/memory.jl:77-95`).
- Chat history is a separate JSON file `~/.kamila_chat_history.json` (`src/bridge.jl:56-80`) with the same weaknesses.

## Design

- **Storage:** SQLite via `SQLite.jl`. File `~/.local/state/kamila/kamila.db` (or `~/.kamila.db` if that path is preferred; configurable via `KAMILA_DB`). Keep `~/.kamila_memory.json` as a read-only export/compat view regenerated on demand.
- **Schema v1** (migration-ready; `PRAGMA user_version`):
  - `tasks(id INTEGER PK, title TEXT, description TEXT, category TEXT, priority INT, estimated_time INT, due_date TEXT, created_date TEXT, completed INT, completed_date TEXT, tags TEXT)`
  - `goals(id INTEGER PK, goal TEXT, category TEXT, priority INT, completed INT, progress INT, created_date TEXT, completed_date TEXT)`
  - `achievements(id INTEGER PK, title TEXT, description TEXT, date TEXT)`
  - `chat_messages(session TEXT, role TEXT, content TEXT, created_at TEXT, idx INTEGER)`
  - `kv(key TEXT PK, value TEXT)` — settings/usage stats
  - `migrations(version INT PK, applied_at TEXT)`
- **Data access layer:** extend `KamilaMemory` with typed functions (`get_tasks(;filters)`, `upsert_task`, `record_activity`, ...) over a single `DB` handle. Keep existing function names as thin wrappers so `TaskManager`/tools don't change call sites.
- **Atomicity:** all writes in transactions; WAL mode (`journal_mode=WAL`) for crash safety + concurrent readers.
- **Concurrency:** one connection guarded by a lock in the bridge process (single-threaded loop today); document that future daemon work (`06.1`) will need a connection pool.
- **Migration runner:** on startup, compare `user_version` to the latest schema; apply pending migrations in order; log each via `01.3`.

## Acceptance Criteria

- [x] Migration from a legacy `~/.kamila_memory.json` to DB imports tasks/goals/achievements/stats losslessly.
- [x] Chat history survives a restart.
- [x] `user_version` migration runner is idempotent (running twice is a no-op).

## Risks & Mitigations

- **Risk:** Adding SQLite changes startup time / first-run behavior. **Mitigation:** lazy-open DB on first access; benchmark startup stays < 2 s.
- **Risk:** Breaking `TaskManager` semantics during rewrite. **Mitigation:** keep public function names/signatures; rely on `01.1` tests as the safety net.
- **Risk:** Migration bugs for real user data. **Mitigation:** `import_memory` never mutates the source JSON; migration is copy-in (DB file is new), original JSON retained until user confirms.

# 03.3 — Episodic Summarization

## Objective

Build a rolling **episodic memory**: sessions compressed into durable summaries that are themselves recallable, so Kamila can remember "what happened" over days and weeks without a 10-turn window. Summaries are generated (model-assisted) and stored as first-class memory objects.

## Current State

- Chat context is a sliding window: `MAX_HISTORY=10` (`src/ai/agent.jl:11`), `MAX_CHAT_HISTORY=20` (`src/bridge.jl:48`). Everything older is discarded irreversibly.
- No session concept, no day/week aggregation, no automatic summarization despite `generate_summary` existing as a *static* printout (`src/memory/memory.jl:185-204`).
- `get_today_achievements` filters by exact date string match (`src/memory/memory.jl:100-109`) — no narrative, no cross-session synthesis.

## Design

- **Session model:** each chat session gets an `id` + `started_at`; turns are tagged with `session_id` in the DB (`03.1`).
- **Triggers:** summarize when (a) session ends (bridge shutdown / session switch), (b) a session exceeds N turns (e.g. 30), producing a *segment* summary, or (c) daily rollup at first interaction after midnight.
- **Summarization job:** `Episodic.summarize_session(session_id)` collects raw turns, calls `OllamaInterface.query_ollama` with a strict summary prompt, and stores a `memories` row `kind="episodic", content=<summary>, importance=<decay-weighted>`. Runs **async** (spawned task) so it never blocks the user.
- **Hierarchy:** day-summary summarizes segment-summaries; week-summary summarizes day-summaries. Each layer stored as its own memory with `period` metadata (`start`/`end`).
- **Importance & decay:** each episodic memory gets `importance`; older summaries decay (multiply by `decay^(days_since)`), so recall favors recent but long-running threads stay retrievable. `recall_log` records the decay application.
- **Prompt injection:** `Episodic.build_context(query)` returns relevant day/week summaries (via `03.2` recall) for `03.4` to place in the system prompt.
- **Failure handling:** summarization failure (model down) → store a placeholder `"<summary unavailable: reason>"` with `retryable=true`; retried on next trigger. Never fabricate content.

## Risks & Mitigations

- **Risk:** Summarization cost (extra model calls). **Mitigation:** only on session end / threshold / daily; throttled; small `max_tokens` (400–600) for summaries.
- **Risk:** Async job racing DB writes. **Mitigation:** summaries written through the same locked `MemoryDB` handle (`03.1`); triggered jobs are serialized.
- **Risk:** Summaries drift from truth. **Mitigation:** store source `session_id` + raw-turn count on the summary row; `recall` can expand to raw turns on demand; never present a summary as a verbatim transcript.

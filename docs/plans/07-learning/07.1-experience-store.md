# 07.1 — Experience Store

## Objective

Record Kamila's operational history as **structured experience** — the goals, plans, tool calls, outcomes (verified/failed via `04.3`), and user feedback — so that (a) it can be semantically recalled later (a "I've done this before" memory), and (b) it becomes the dataset for `07.2` fine-tuning and `07.3` preference learning.

## Current State

- `03.2` stores `memories` of kind `chat/task/goal/note/document` but not structured *action → outcome* records with verification status.
- `04.3` produces verification results but they are not persisted as an auditable experience log (only per-step `result`/`verify`).
- There is no dataset export; `01.3` logs events but they are ephemeral.

## Design

- **Experience record** (`experience` table, Migration 8):
  ```sql
  experience(id INTEGER PK, ts TEXT, kind TEXT,       -- 'plan' | 'tool' | 'conversation'
             goal TEXT, plan_id TEXT, step_id INT,
             prompt TEXT, tool TEXT, args TEXT, result TEXT,
             verified INT,           -- outcome from 04.3
             role TEXT,              -- assistant | user | system
             feedback INT NULL,      -- -1 dislike, 0 neutral, +1 like (from 07.3)
             cost_tokens INT, duration_ms INT)
  ```
- **Hooks:** `04.1.mark_step` (verified outcome), `04.2` batch results, `01.3` handlers all write `Experience.record`. Writes are best-effort, non-blocking, batched (flush every 5 s or 50 rows).
- **API:** `Experience.record(...)`, `Experience.search(query; k=10, verified=true)` (reuse `03.2` embedding over the `prompt` column), `Experience.similar_solution(query)`, `Experience.export(; format=:jsonl)`.
- **"Do this again" retrieval:** bridge route `experience.reuse <description>` → returns the top verified experience (steps + args) as a template the model can adapt — baked into `05.2` skill self-registration as a source.
- **Pruning:** dedupe near-identical records (embedding threshold); cap table (default 50,000 rows, oldest pruned); exit-interview style: a failed plan still records the failure with `verified=0` so training data includes negatives.

## Acceptance Criteria

- [ ] Completing a plan step (verified) produces a queryable experience record.
- [ ] Paraphrased recall returns the planted verified solution before an unrelated one.
- [ ] `verified=false` records are stored (for future training) but excluded from `similar_solution(verified=true)`.
- [ ] Dedupe prevents runaway growth on repeated tasks.
- [ ] Export yields valid JSONL consumable by `07.2`.
- [ ] Recording never blocks or slows the interactive path.

## Risks & Mitigations

- **Risk:** Storage growth and privacy. **Mitigation:** prune cap, local-only storage, `experience.export` is user-invoked (not automatic), opt-out config `experience.enabled=false`.
- **Risk:** Near-identical queries bloat. **Mitigation:** embedding-hash dedupe; expiry for low-importance rows.
- **Risk:** Reuse hallucinates a "known" solution. Mitigation: reuse returns *records*, never fabricated; model must still verify; audit fields on the record.

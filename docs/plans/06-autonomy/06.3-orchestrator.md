# 06.3 — Orchestrator

## Objective

Synthesize the autonomy pieces into a bounded **orchestrator**: a scheduler that decides *what to work on next* among active plans (`04`), daemon jobs (`06.1`), and goals (`06.2`), and dispatches work within a **daily budget** and capability constraints (`05.3`). This is Kamila's first real "executive loop" — but a tightly governed one.

## Current State

- No notion of "what should I do now" exists. Work only happens when a user sends a request (`src/bridge.jl:284-378`).
- Schedules exist only as inert outputs: `TaskManager.generate_timetable` (`src/tasks/task_manager.jl:221-249`) and `generate_daily_report` — advisory text, never executed.
- Nothing prioritizes across plans, goals, and reminders.

## Design

- **Work item model:** `orchestrator` consumes three sources, each yielding "runnable units":
  - `PlanStep` ready to run (`04.1.next_runnable`), from active plans (`status==:active` or `:paused` with resume policy).
  - `ScheduledJob` due now (`06.1`).
  - Goal-level "advance" nudge (run the next step of a goal's plan when budget allows).
- **Prioritization (deterministic, not LLM-decided):**
  1. User-requested work (interactive always wins — the orchestrator yields to the bridge).
  2. Due scheduled jobs with `urgency=critical`.
  3. Overdue plan steps / goals.
  4. Plan steps by priority (from `Plan.metadata.priority`) then age.
  5. Maintenance (memory compaction, summarization, skill re-index).
- **Budget governor:** daily caps config `orchestrator.daily_actions` (default 20), `orchestrator.daily_model_calls` (default 40), `orchestrator.max_autonomous_duration_min` (default 60). Budget spent → orchestrator idles until next day or user resets. All autonomous actions logged with budget debit (`01.3`).
- **Autonomy window:** by default the orchestrator **proposes** work to the user (notification: "I could advance plan X — run now?"); it **executes** autonomously only under an explicit per-session toggle (`orchestrator.auto_execute=false` default) or a per-item capability grant. This keeps `06` honest: autonomy is bounded and revocable.
- **Failure handling:** a step that fails verification (`04.3`) is marked and the orchestrator stops dispatching that plan (pauses it) and reports; it does **not** silently retry destructive work.
- **Catch-up:** on boot, orchestrator reviews plans/goals for overdue steps and either proposes or (if auto-execute) runs them within budget.

## Acceptance Criteria

- [ ] With `auto_execute=false` (default), the orchestrator never runs a plan step without user approval.
- [ ] Budget exhaustion stops dispatch (unit test: set daily_actions=1, confirm no second action).
- [ ] Interactive request preempts any autonomous dispatch.
- [ ] A verify-failed step pauses its plan and is reported, not silently retried.
- [ ] Boot catch-up proposes (not runs) overdue work under default policy.
- [ ] Budget debits are auditable per action.

## Risks & Mitigations

- **Risk:** Autonomy runaway (the core fear). **Mitigation:** propose-first default, hard budgets, capability scoping (`05.3`), pause-on-failure, and a global kill switch (`orchestrator.pause` route + config). Document the kill switch prominently.
- **Risk:** Orchestrator competes with interactive TUI for the DB/model. **Mitigation:** interactive requests always win (yield), single-writer DB lock (`03.1`), model calls budgeted.
- **Risk:** Catch-up floods the user with proposals. **Mitigation:** proposal rate-limit (max 3 distinct proposals/day) + Snooze.

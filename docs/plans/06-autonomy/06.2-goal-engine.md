# 06.2 — Goal Engine

## Objective

Turn user-declared goals into **live, tracked, decomposed plans** that the orchestrator (`06.3`) and daemon (`06.1`) advance over time — not just strings in a JSON file. Today `KamilaMemory.add_goal` stores a goal as `{goal, category, priority, completed}` (`src/memory/memory.jl:114-135`) and `get_active_goals`/`complete_goal` just flip a boolean (`src/memory/memory.jl:140-180`). There is no decomposition, no progress, no scheduling.

## Current State

- Goals are passive records; `progress` is stored but never computed or updated.
- `complete_task` in `TaskManager` (unrelated `src/tasks/task_manager.jl:181-199`) and `complete_goal` in memory are manual boolean flips.
- No link between a goal and the tasks/plans that advance it.
- `memory_query goals` renders a hardcoded progress bar from `progress // 10` units (`src/ai/tools.jl:645-649`) even though nothing ever sets `progress`.

## Design

- **Goal → plan binding:** a goal gains `plan_id` (reference to a `04.1` Plan). On creation (or on demand), the goal engine runs the decomposer (`04.4`) to produce a plan; the goal tracks plan state.
- **Progress = derived, not stored (or stored/refreshed):**
  - `progress` = (verified steps / total steps) computed from the linked plan, cached to a `goal_progress` column and refreshed on plan changes (`00`-style computed cache).
  - No more manual progress guessing.
- **Goal state machine:** `:proposed → :active → :paused → :completed | :abandoned`. `complete_goal` only succeeds when the linked plan is `:completed`.
- **Incremental progress events:** when the plan advances (a step becomes verified, `04.1`), the goal engine publishes `goal.progress` events on the bus (`06.1`), so the TUI and daemon (daily report) can reflect real movement.
- **Goal-to-task hygiene:** every plan step that has `category`/effort can surface as a user-facing `Task` (`TaskManager`) entry (optional, `goal.sync_tasks=true` default off) so the user sees goals in the existing task UI.
- **Deferred linking:** goals created before this plan exist with `plan_id=null`; the engine can retro-decompose on demand (`goal.decompose <id>` bridge route).

## Acceptance Criteria

- [ ] Creating a goal produces a plan whose verified-step ratio drives the goal's `progress`.
- [ ] `complete_goal` on an incomplete plan is rejected.
- [ ] A `goal.progress` event fires exactly once per advancing step (no duplicates).
- [ ] Old goals (no plan) still list and can be retro-decomposed.
- [ ] The hardcoded `repeat("▓", progress ÷ 10)` output is replaced by derived progress.

## Risks & Mitigations

- **Risk:** Decomposing every goal eagerly is expensive. **Mitigation:** decomposition is on-demand (button/route), not automatic on every goal add.
- **Risk:** Progress semantics confuse users (is "2/3 steps" the same as "66% effort"?). Mitigation: label clearly as *step progress* and optionally weight by estimated time.
- **Risk:** Circular dependency goal↔plan↔task. Mitigation: plan is the source of truth for progress; goal/task are projections. Document read-only projections.

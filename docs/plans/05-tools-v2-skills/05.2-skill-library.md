# 05.2 — Skill Library

## Objective

Make skills **first-class, persistent, versioned, and runtime-growable**. Today `get_all_tools()` is a hardcoded constant (`src/ai/tools.jl:692`); the only way to add a capability is editing Julia and recompiling. This plan introduces a skill registry so skills can be installed, disabled, versioned, and (critically, for autonomy) **self-registered by the agent at runtime**.

## Current State

- `Tool` struct + `get_all_tools()` returns a hardcoded `Vector{Tool}` (`src/ai/tools.jl:13-18,692-827`).
- `execute_tool` dispatches by exact (normalized) name against that list (`src/ai/tools.jl:831-857`).
- No persistence, no versioning, no enable/disable, no plugin seam. `docs/Kmila.json` describes a `plugin_folder: "tools/"` + `auto_load` idea but it is aspirational — no code implements it.

## Design

- **Skill record** persisted in SQLite (via `03.1`, `Migration 5`):
  ```sql
  skills(id TEXT PK, name TEXT, version TEXT, spec TEXT /* ToolSpec JSON */,
         impl_type TEXT, impl_ref TEXT, enabled INT, source TEXT,
         created_at TEXT, updated_at TEXT)
  ```
  - `impl_type`: `:julia` (function ref in `src/ai/skills/`), `:shell` (a command wrapper), `:prompt` (model-call skill), `:delegated` (a sub-agent skill).
  - `impl_ref`: module + function symbol for `:julia`; the command template for `:shell`; the prompt for `:prompt`.
- **Built-in vs installed:** built-in skills (the 13 core) are seeded from source into the registry at init; installed skills are user/agent-added records. Built-ins are not deletable, only `enabled=0`.
- **Loader:** `src/ai/skills/loader.jl` loads enabled skills from the registry, plus a scan of `~/.config/kamila/skills/*.jl` (user Julia skills) — each file may `register_skill(spec, impl)`.
- **Runtime self-registration (agent-driven):** a `learn_skill` tool (permission-gated, `:ask` by default) lets the agent capture a **reusable procedure** as a `:prompt` or `:shell` skill: the model describes the procedure, parameters, and (optionally) example invocation; the runtime stores it with `source="agent"`, `enabled=false` until the user approves. This is the seed of "acquiring new skills" (AGI-assessment §3.3) — still curated, not weight-updating.
- **Versioning:** spec changes bump `version`; `05.1`'s schema validation uses the active version; `skills list` shows version + source + enabled.
- **Bridge routes:** `skills.list`, `skills.enable/disable`, `skills.install` (from JSON spec), `skills.uninstall`, `skills.show`. TUI panel to manage.
- **Caps:** `max_skills=100`, `max_spec_size=16 KB`, shell skills restricted to a **command template allowlist** (`{input}` interpolation only) enforced by `05.3`.

## Acceptance Criteria

- [ ] The 13 built-ins are registered, enabled, and functionally identical to today.
- [ ] Installing a JSON skill spec makes it callable next turn (no recompile).
- [ ] Disabling a skill removes it from `get_all_tools()`.
- [ ] `learn_skill` can register a prompt-skill that passes a canned "reuse" test (execute it twice, same procedure).
- [ ] Shell skills cannot bypass the template allowlist.
- [ ] A restart preserves registry state (persisted).

## Risks & Mitigations

- **Risk:** Agent-registered skills are arbitrary code/procedures. **Mitigation:** default `enabled=false` + `:ask` approval; `:shell` skills template-allowlisted; `:prompt` skills are just prompts (no code). User can inspect spec before enabling.
- **Risk:** Loading user Julia files breaks the process on bad code. **Mitigation:** isolated `include` in a sandboxed module with try/catch; failure logs (`01.3`) and skips, never aborts.
- **Risk:** Registry drift between DB and built-ins. **Mitigation:** seed idempotently on init; built-in version bump re-seeds spec while preserving `enabled` flag.

# 05.1 — Native Function Calling

## Objective

Replace the primary agent→tool mechanism from "model emits text JSON that we scrape with regex" (`02.5` was the stopgap) to Ollama's **native JSON-schema tool calling**, where the model emits structured `tool_calls` in the API response and the runtime validates them against schemas. Keep the text parser only as a graceful-degradation fallback.

## Current State

- `query_ollama_chat_stream` (`src/ai/ollama_interface.jl:174-225`) posts `messages` to `/api/chat` and reads `message.content` — it **never passes a `tools` array**, so the model has no structured tool schema; it can only emit text.
- Tool discovery is `get_all_tools()` returning `Tool(name, description, parameters::Dict, func)` (`src/ai/tools.jl:13-18,692`); `parameters` are **descriptions, not JSON-schema**, and are injected into the system prompt as a JSON dump (`src/ai/agent.jl:15-24,46-47`).
- The model must then "fake" tool calls in prose; the runtime recovers them via `parse_response` (`src/ai/agent.jl:138`) / `parse_response` (`src/ai/agent_stream.jl:210`).
- `OllamaInterface.query_model` (`src/ai/model_router.jl:274-303`) also uses `/api/generate` without tools.

## Design

- **Schema-first tool definitions:** introduce `ToolSpec` = `{name, description, parameters::Dict (JSON Schema), strict::Bool}`. Derive JSON Schema from the current `Tool.parameters` dictionary (types: string/int/bool, required list, defaults) with a migration script so existing tool descriptions become valid schemas.
- **Native protocol:** extend `query_ollama_chat_stream` and `query_ollama_chat` to accept `tools::Vector{ToolSpec}`; pass `"tools" => [tool spec]` in the `/api/chat` payload (and `"tool_choice" => "auto"`). Parse `message.tool_calls` from the response when present (Ollama returns `{message:{tool_calls:[{function:{name,arguments}}]}}`).
- **Tool loop unification:** `AgentStream` and `bridge.handle_ai_query` consume either (a) native `tool_calls` (preferred) or (b) text-parsed calls (`02.5`) when the endpoint or model lacks tool support (capability-detected via `get_model_info`'s `capabilities` field, `src/ai/model_router.jl:102-120`).
- **Validation:** native args are validated against the schema before execution (`validate_schema` — use `JSONSchema.jl` or a minimal validator). Invalid → `:validation` error (`01.4`) returned as the tool result so the model self-corrects.
- **Compatibility:** keep `get_all_tools()` and `execute_tool(name, args::Dict)` signatures; add `get_tool_specs()` and `execute_tool_validated(tool_name, args, spec)`. The system prompt switches to listing tool *names + brief hints* (schemas go via the API), reducing prompt bloat.

## Acceptance Criteria

- [ ] A model with native tool support emits `tool_calls`; Kamila executes them without any text-JSON scraping.
- [ ] A model without tool capability still works via the `02.5` text parser (graceful fallback).
- [ ] Args failing schema validation produce a `:validation` error the model can recover from.
- [ ] `get_all_tools()` callers (tests, TUI) keep working unchanged.
- [ ] System prompt no longer contains the full 13-tool parameter dump.

## Risks & Mitigations

- **Risk:** Ollama tool-call response shape varies by version/model. **Mitigation:** capability detection + defensive parse (both `tool_calls` shapes seen in the wild) + text fallback keeps it robust; fixtures locked in `test/tool_spec_test.jl`.
- **Risk:** Schema migration mislabels required args. **Mitigation:** derive required from existing defaults; audit each of the 13 tools in the migration test (assert `required` covers the documented "required" params in `tools.jl` descriptions).
- **Risk:** Some models ignore schemas. **Mitigation:** `tool_choice:"auto"` + validation errors as recovery; per-model capability gate.

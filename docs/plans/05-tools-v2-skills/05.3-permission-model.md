# 05.3 — Permission Model

## Objective

Formalize the ad-hoc policy from `02.2-tool-permission-redesign` into a **capability-based permission model** integrated with the skill library (`05.2`), the batch orchestrator (`04.2`), and sub-agents. The goal: every action — built-in or skill, direct or delegated — is traceable to a capability check, and `force`-style bypasses are cryptographically impossible for untrusted callers.

## Current State

- `02.2` delivers the policy file (`~/.kamila_policy.json`), `Permission.evaluate`, session cache, and HMAC capability tokens — but it only gates `run_shell_command`, `write_file`, `set_reminder` (`src/ai/tools.jl` call sites), and nothing yet consumes capability tokens.
- `force=true` is still a tool parameter (`src/ai/tools.jl:42,53`) with token support designed but unused.
- Skills (`05.2`) and batches (`04.2`) are new attack surfaces with no permission integration yet.
- `Auth` (`src/security/auth.jl`) gates *human login*, not *tool calls*.

## Design

- **Capability tokens (design finalized from `02.2`):**
  - A token = `{tool, arg_hash, action:"allow", issued_at, exp, nonce}` signed with HMAC (per-session secret from `Auth`).
  - Any tool call may carry `capability` (a token string). The runtime **verifies** it: signature, expiry, exact `(tool, arg_hash)` match. Forged/expired/mismatched tokens → `:permission` deny.
  - `force=true` is **removed as a bypass**: it is only a hint that a valid capability token should be attached. No token ⇒ policy decides (`:ask`/`:deny`).
- **Scope propagation:** a batch (`04.2`) or sub-agent (`04.2.delegate`) receives a **restricted capability set**: the union of its own tokens, each further narrowed by (a) skill-level grants and (b) depth. A sub-agent can never mint tokens beyond its parent's set.
- **Skill grants:** each skill (`05.2`) declares `required_capabilities` (e.g. `:files.write`, `:shell`, `:network`). Enabling a skill is gated on the user granting those capabilities; capability downgrade is tracked.
- **Policy semantics extended:**
  - Rules now can target `skill:<name>` and `cap:<capability>`.
  - New `default_capabilities` in policy (e.g. `["memory.read", "tasks.read"]` by default, which is why `list_tasks`/`memory_query` remain prompt-free).
  - `ask` results may mint a short-lived token (`TTL=60s`) so a multi-call batch doesn't re-prompt.
- **Audit:** every capability check writes `{"event":"capability.check","tool":...,"cap":...,"token_id":...,"decision":...,"rule":...}` (`01.3`). `permission.decisions` returns them; TUI shows "why this was allowed".
- **Belt-and-suspenders:** even with a valid token, hard-blocked patterns (the `rm -rf /`, `shutdown`, `mkfs` deny rules) remain denied — a capability token cannot override a deny rule.

## Acceptance Criteria

- [x] A forged or expired capability token never bypasses policy.
- [x] `force=true` without a valid token behaves exactly per policy (default `:ask`).
- [x] Deny rules (e.g. `rm -rf /`) cannot be overridden by any token.
- [x] A sub-agent cannot invoke a tool outside its parent's narrowed capability set.
- [x] Enabling a skill requires its declared capabilities to be granted.
- [x] Every decision is auditable via `capability.audit`.

## Risks & Mitigations

- **Risk:** Tightening permissions breaks the agent's normal flows (asks everywhere). **Mitigation:** generous `default_capabilities` (read/memory/task ops), short-lived ask tokens for batch contexts, and a `session_remember` cache so identical calls don't re-prompt.
- **Risk:** Token logic is security-critical and subtle. **Mitigation:** HMAC secret held in `Auth` (already hashed/salted infra), constant-time comparison, clock-skew tolerance (±60 s), and dedicated tests including property tests on arg-hash canonicalization (JSON key sort).
- **Risk:** Sub-agent capability narrowing is complex. **Mitigation:** start with depth-limited **intersection** (child caps = parent caps ∩ declared child needs); document monotonicity (a child never gains capabilities).

## Implementation Notes

- Work item 1 (`src/security/capability.jl`) is a new `Capability` module: tool→capability map (`TOOL_CAPABILITY`), HMAC-signed tokens (`{tool, arg_hash, action, issued_at, exp, nonce}`) with constant-time verification, clock-skew-tolerant expiry, one-shot nonce replay protection, `restrict_caps` scope intersection, and an audit ring (`capability.audit`).
- The richer `Capability.verify_capability` coexists with the legacy `Permission.verify_capability`; `_authorize!` accepts either, so existing 02.2 tokens keep working.
- `arg_hash` excludes the `capability`/`force` control keys so a token minted for an action verifies once the caller attaches its token.
- `Permission._evaluate_with_rule` now honors `default_capabilities` (after rules, so a deny rule always wins) and `cap:<cap>`/`skill:<name>` rule targets. `granted_cap` gates skill install/enable.
- Scope propagates through `execute_tool_raw`/`_authorize!` → batch `preflight_batch`/`execute_batch`/`batch_structured` → `delegate` → `run_agent_sync`, so a child sub-agent can never exceed its parent's capability set (intersection).
- `force` is confirmed to be hint-only: grep shows the only `force` in tools.jl is the stdlib `cp(...; force=true)` and the docstring; no tool path reads a model-supplied `force` to skip policy.
- `test/capability_test.jl` (62 tests) covers mint/verify/expiry/replay/mismatch, deny-overrides-token, scope narrowing at every layer, skill gating, and the bridge routes.

# 04.4 — Task Decomposition

## Objective

Enable the agent to **decompose** a large goal into a dependency-resolved DAG of sub-tasks automatically, produce a plan (`04.1`), and monitor progress — the "break work into discrete ordered steps" behavior the planning prompt already asks for (`src/ai/agent.jl:73-92`), now enforced by machinery instead of prose.

## Current State

- Decomposition only happens inside the LLM's head: the planning *mode* prompt asks for numbered steps (`src/ai/agent.jl:77-82`) but nothing captures them as a structured, executable plan.
- No dependency resolution, no cycle detection, no progress tracking across decomposition.
- `TaskManager` tasks are user-facing to-dos, not executable agent plan steps (`src/tasks/task_manager.jl`).

## Design

- **Decomposer** `src/planning/decompose.jl`:
  - Input: `goal` (string), optional `hints` (constraints, resource caps).
  - Calls the model with a strict decomposition prompt requesting JSON:
    ```json
    {"steps": [
       {"id": 1, "description": "...", "depends_on": [], "verify": {"kind":"file_exists","target":"..."} | null,
        "tools_hint": ["write_file", "run_shell_command"]},
       ...
    ]}
    ```
  - **Validation & repair:** reject empty steps, duplicate ids, missing `description`, dependency on unknown id, and **cycles** (DFS). On invalid JSON, retry once with the parse error fed back (`02.5` parser + `01.4`); on second failure, fall back to a single "do it directly" step so the task still works.
  - **Size limits:** cap steps (default 20) and depth of nested decomposition (default 2). Over-limit → suggest splitting the goal, or take the top-N and a trailing "remaining work" step.
- **Decomposition on demand:** the `plan.create` bridge route (`04.1`) gains `plan.decompose(goal)` that runs the decomposer then persists the plan. Also available as a model-callable tool `decompose_goal`.
- **Progress synthesis:** a step that itself is large (estimated by model or by >N words) may be re-decomposed into a **sub-plan** (plan-within-plan) rather than a single step; the sub-plan is executed by `04.2.delegate` (sub-agent) and its completion marks the parent step `:verified`.
- **Interruptible:** decomposition is async (streamed events); user can cancel during decomposition.

## Acceptance Criteria

- [x] `decompose("build a small web server")` yields a valid, acyclic plan persisted to DB.
- [x] A goal that needs more steps than the cap produces top-N + "remaining work" (never silently drops work).
- [x] Recovering from two bad JSON responses yields a single "do it directly" step (task still completes).
- [x] A large step can become a sub-plan that executes via sub-agent and marks the parent verified.
- [x] User can cancel during decomposition without corrupting state.

## Risks & Mitigations

- **Risk:** Decomposition quality varies by model. **Mitigation:** validation + repair + fallback keeps it robust; steps carry `verify` specs (`04.3`) so even a bad decomposition fails loudly, not silently.
- **Risk:** Infinite nesting of sub-plans. **Mitigation:** global depth cap (2) + step cap; exceeded → collapse to direct execution.
- **Risk:** Decomposition prompt cost. **Mitigation:** one-shot with retry-once; streaming so latency is perceived as progress.

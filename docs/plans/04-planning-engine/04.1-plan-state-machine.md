# 04.1 — Plan State Machine

## Objective

Introduce a first-class, **persisted** `Plan` object with an explicit lifecycle (created → pending → active → completed / failed / cancelled), step-level states, dependencies, and resumability. The agent executes *a plan*, not a stateless loop; on crash or tool failure it can resume from the last completed step.

## Current State

- `AgentStream.run_agent_stream` (`src/ai/agent_stream.jl:43-149`) is a `while iteration < max_iterations` loop with no plan structure; `history` is just an untyped vector of tuples (`src/ai/agent_stream.jl:53`).
- `bridge.handle_ai_query` has `max_tool_loops = 5` (`src/bridge.jl:310`) with the same shape.
- `TaskManager.generate_timetable` produces a greedy time table (`src/tasks/task_manager.jl:221-249`) but it is **not** an executable plan and is unrelated to agent execution.
- Nothing persists an in-progress multi-step task.

## Design

- **Plan type** `src/planning/plan.jl`:
  ```julia
  mutable struct Plan
      id::String
      goal::String
      status::Symbol          # :created, :pending, :active, :paused, :completed, :failed, :cancelled
      steps::Vector{PlanStep}
      created_at, updated_at::DateTime
      session::String
      metadata::Dict
  end
  mutable struct PlanStep
      id::Int
      description::String
      status::Symbol          # :pending, :running, :verified, :failed, :skipped
      depends_on::Vector{Int}
      tool::String            # tool name or :verify / :delegate
      args::Dict
      result::Union{Nothing,String}
      attempts::Int
  end
  ```
- **Lifecycle rules (the state machine):**
  - `Plan.create(goal) -> :created`; `Plan.start(p) -> :active`.
  - A step is runnable iff all `depends_on` steps are `:verified`.
  - Step transitions: `:pending → :running → :verified | :failed`. `:failed` with `attempts < max_retries` → back to `:running` (with new args allowed).
  - On tool error classified `:retryable` (`01.4`), step retries; on non-retryable, step → `:failed`, plan → `:failed` (unless a `fallback_step` exists).
  - Plan → `:paused` on user interrupt or session switch; `:completed` when all steps `:verified`.
- **Persistence:** `plans` + `plan_steps` tables via `03.1` (`Migration 3`). `Plan.load(active=true)` restores in-progress plans across restarts.
- **API:** `create`, `start`, `next_runnable(p)`, `mark_step(p, id, status, result)`, `pause`, `resume`, `cancel`, `list(;status)`.
- **Bridge routes:** `plan.create`, `plan.list`, `plan.status`, `plan.cancel`, `plan.resume`; TUI panel to view/control the active plan.
- **Model integration:** the system prompt (`04.3`/`agent.jl`) instructs the model to emit plan-step JSON for complex tasks; for simple tasks it still answers directly (strategy/flexibility preserved — `src/ai/agent.jl:33-38`).

## Acceptance Criteria

- [x] A plan with steps A→B→C runs in dependency order and only C after B verified.
- [x] A `:retryable` tool failure retries (max 3); a `:permission` failure fails the step immediately.
- [x] Pausing mid-plan and restarting the process resumes at the correct step (DB-backed).
- [x] Cancelling a plan marks it `:cancelled` and no further steps run.
- [x] Simple tasks still bypass the plan machinery (no behavior regression — `run_agent_stream`/`run_agent_sync` untouched, full suite green).
- [x] All `01.1` agent tests pass.

## Risks & Mitigations

- **Risk:** Refactoring the agent loop breaks streaming/TUI. **Mitigation:** keep `run_agent_stream` signature/events identical; add bridge round-trip tests; CI smoke gate.
- **Risk:** Plans grow unbounded. **Mitigation:** plan size cap (default 50 steps), auto-archive completed plans after 7 days.
- **Risk:** Model emits invalid plan JSON. **Mitigation:** validation on `create` (steps require description; ids unique; dependencies acyclic — reject cycles).

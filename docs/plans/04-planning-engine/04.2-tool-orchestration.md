# 04.2 — Tool Orchestration

## Objective

Overcome the one-tool-at-a-time constraint ("You can only call ONE tool at a time", `src/ai/agent.jl:43`) with safe **parallel tool execution**, fan-out/fan-in within a plan step, and delegation to sub-agent tasks — all while preserving determinism, permission checks, and auditability.

## Current State

- The agent loop awaits one tool per iteration (`src/bridge.jl:312-360`, `src/ai/agent_stream.jl:56-145`).
- No concurrency: `run_shell_command`, `web_search`, `read_file` all serialize.
- No sub-agent concept: `AgentStream.run_agent_stream` is called once per top-level query (`src/bridge.jl:391-414`).
- Permissions (`02.2`) are per-tool-call; nothing coordinates multi-call consent.

## Design

- **Batch call:** extend the tool-call JSON contract so a single model turn can request a *batch*:
  ```json
  {"tool": "batch", "calls": [
     {"tool": "read_file", "args": {"file_path": "a"}},
     {"tool": "web_search", "args": {"query": "x"}}
  ]}
  ```
- **Executor** `src/planning/orchestrator.jl`:
  - Validates the batch against `02.2` permissions **first** (all-or-nothing preflight per batch; if any call would require `:ask`, ask once for the batch).
  - Runs independent calls concurrently on a bounded thread pool (`Threads.@spawn` or a `Channel`-based worker pool; default 4 workers, config `orchestrator.parallelism`).
  - Calls sharing a mutable resource (e.g. same file, DB writes) are automatically serialized via a resource-lock map.
  - Collects results in call order; returns a structured array `[{call, result, ok}]` so the model sees per-call status.
  - **Timeout per call** (default 30 s) so one hung `run_shell_command` can't stall the batch.
- **Sub-agents:** `orchestrator.delegate(sub_prompt, plan_step)` spawns a child `run_agent_sync`/`run_agent_stream` (`src/ai/agent_stream.jl:153-206`) as a sub-plan step with its own plan id (`04.1`), result returned to the parent step. Depth cap (default 3) prevents runaway nesting.
- **Fan-in:** a step may depend on multiple sub-agent results (`depends_on` list in `04.1`); the step runs only when all are `:verified`.
- **Observability:** each batch/sub-agent emits structured events (start/finish/duration, per-call) via `01.3`; surfaced as `tool_call`/`tool_result` streams to the TUI.

## Acceptance Criteria

- [x] Two independent tools in a batch complete concurrently (elapsed time test with injected delays).
- [x] A batch containing a denied call is denied up front (no partial execution).
- [x] Same-file concurrent writes are serialized (result is deterministic).
- [x] One hung call times out without killing the batch or the bridge.
- [x] Sub-agent delegation respects depth cap; result returns to parent step.
- [x] No regression: single-tool calls behave exactly as before.

## Risks & Mitigations

- **Risk:** Concurrency bugs (races, deadlock). **Mitigation:** bounded pool, resource locks, per-call timeout, deterministic collection in call order; stress test in CI.
- **Risk:** Parallel `run_shell_command` prompts spam user. **Mitigation:** one permission ask per batch (preflight), not per call.
- **Risk:** Model abuse (huge batches). **Mitigation:** max calls per batch (default 8) + total result byte cap.
